# Demo 流程需求與實作計畫

## 流程原則

1. Demo 登入頁直接顯示 `user / password`，並明示正式版應改接手機、自然人憑證或健保卡驗證。
2. username 對應一份本機錢包檔案；密碼不得寫入檔案。
3. Mock 政府資料庫有紀錄不代表民眾已有憑證；新帳號的憑證錢包必須從空白開始。
4. Agent 推薦服務時不得讀取個人資料。
5. 民眾選定服務後，Agent 必須先列出每項資料的取得方式。
6. 政府資料必須顯示發證／持有部門，再由民眾授予本次用途的最小權限。
7. Agent 授權狀態以 username 持久化，重新登入後仍保留；每次實際向機關取資料前仍顯示用途並請民眾確認。
8. 缺少或過期的政府憑證必須先依發證機關要求取得必要資訊；例如近期就醫憑證需要健保卡號與就醫日期，戶籍憑證需要戶籍地址與設籍日期。
9. 同一批憑證需要的重複資料只能輸入一次，再由後端分送各個 Mock 發證 API。
10. 後端模擬發證機關驗證後，自動產生憑證編號與效期並存入本機錢包；申請欄位不得放入語言模型 context。
11. 政府通常不持有的文件必須由民眾上傳，不得偽裝成跨機關自動取得。
12. 政府調閱完成但文件未齊時，流程停在「等待補件」，不得先判定資格。
13. 資格只能由後端規則引擎依已取得證據判斷。
14. 側欄永久顯示憑證錢包、效期、授權狀態與曾使用的服務。
15. 文件內容不得提供給對話模型；目前 Demo 只在記憶體保存檔名、類型、大小與上傳時間。
16. 皮夾介面必須區分官方已公開的試營運案例與本 Demo 的概念憑證；概念憑證一律標示 `Demo Mock`，不得暗示為現行 TW DIW 正式卡片。
17. 「本次資料來源與取得方式」預設保持收合；憑證申請資料改在獨立卡片輸入，不依賴展開資料來源。
18. 每個 username 的案件編號、服務名稱與狀態必須持久化於使用者資料，並在側欄提供快速查詢。
19. 頁面底部提供紅色 Demo 重設按鈕，清除目前 username 的憑證與案件資料後回到登入頁。
20. 每次正式送件時必須將當次授權、資料取得、資格判斷、草稿與確認紀錄凍結為案件級 Audit Log；查詢案件時可展開完整時間線。

## 資料分類

| 類型 | 例子 | Demo 行為 |
|---|---|---|
| 政府憑證 | 戶籍、親子關係、所得級距、就業保險年資 | 顯示部門，取得同意後調閱最小結果 |
| 民眾文件 | 非自願離職證明、租賃契約、醫療費用收據 | 顯示檔案欄位，民眾自行上傳 |
| 過期憑證 | Demo 身心障礙資格憑證 | 側欄標示已過期，不可用於資格判斷 |
| 已授權憑證 | 有效且已持續授權本 Agent 的政府憑證 | 重新登入仍顯示已授權；撤銷後立即變為無可用憑證 |
| 未授權憑證 | 有效但尚未授權本 Agent 的政府憑證 | 側欄標示未授權，同意使用後切換為已授權 |

## 狀態流程

```text
等待提問
  -> 推薦服務
  -> 顯示政府部門與民眾文件
  -> 建立／更新缺少的政府憑證（如需要）
  -> 等待政府資料授權
  -> 取得政府憑證
  -> 等待民眾上傳（如需要）
  -> 規則引擎資格判斷
  -> 建立草稿
  -> 本人確認
  -> 送件
```

## 介面與深模組

`CitizenAgent.send(...)` 仍是 HTTP 與測試共用的唯一流程介面。資料來源分類、授權、文件驗證、資格完成條件與 audit 都藏在 `CitizenAgent` 實作內；前端只根據 session view 渲染，不自行決定哪些資料可由政府取得。
